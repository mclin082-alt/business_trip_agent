# Phase 3 运行说明

Phase 2 验证的是"核心决策链路能不能跑通"：3 个假工具、一个 Plan→Action→
Observation 循环、一个失败点（航班满员）。Phase 3 在这个骨架上做了两件事：

1. **把方案书里完整的工具集补齐**，从 3 个扩到 10 个。
2. **加了一个 Checklist 侧边栏**，对应方案书第四节的 Verifier，任务推进过程中
   实时打勾，而不是"流程跑完就算完成"。

## 这一步做了什么

### 1）补全的工具（新增 7 个，原有 3 个不变）

| 工具 | 作用 |
|---|---|
| `get_customer_info` | 查 CRM：客户公司名称、地址、联系人 |
| `get_my_calendar` | 查自己的日程 |
| `get_customer_calendar`（已有） | 查客户的日程 |
| `get_travel_policy` | 查差旅政策：机票/酒店预算上限 |
| `search_flight`（已有） | 查航班（失败点 1：09:00 满员） |
| `search_hotel` | 查酒店（失败点 2：陆家嘴附近酒店都超预算） |
| `book_flight`（已有） | 订航班 |
| `book_hotel` | 订酒店 |
| `sync_calendar` | 把行程同步成一条日历事件 |
| `send_confirmation_email` | 给客户发确认邮件 |

和 Phase 2 的假工具形式完全一样：都是普通 Python 函数，返回写死在 `MOCK_DATA`
里的假数据，模型通过 tool use 自己判断该调用哪个、传什么参数。

**两个失败点**：
- 航班：09:00 满员，需要模型自己发现客户 10:00 才有空，进而选择仍能满足会面
  时间的备选航班（07:30）。
- 酒店：客户公司在陆家嘴核心区，附近酒店报价都超过 800 元/晚的政策上限，但
  `search_hotel` 的备选列表里有一个稍远（1.8km）但在预算内（780 元）的选项——
  模型应该自己发现并选择它。当前 demo 还没有接入人工审批（那是 Phase 4 才做的
  事），所以遇到超预算不能指望"弹窗批准"，模型需要自己在给定的备选项里找到
  一个合规方案。

### 2）Checklist 侧边栏

对应方案书第四节的 5 项完成标准：

```
☐ 航班已确认
☐ 酒店已确认
☐ 客户会面时间已确认
☐ 日历事件已同步
☐ 确认邮件已发送
```

每次工具返回结果之后，后端会核对一遍这 5 项有没有变化，通过 WebSocket 推一条
`checklist` 消息，前端收到后重新渲染侧边栏的打勾状态和"N / 5 项已完成"的进度。

**这里有个容易问的问题，提前说清楚**：Checklist 打勾这件事是代码做的，不是模型
决定的——这是不是违反了"决策必须由模型现场推理"这条红线？不违反。原因是
Checklist 核对的是"客观事实有没有发生"（比如"`book_flight` 是不是返回了
`success`"），这属于 Verifier（验证器）的职责；而"航班满了该怎么办、该订哪个
酒店"这些才是需要现场推理的决策，这部分完全没有被代码替代。方案书第四、五节
本来就是把"验证"和"决策"分成两层来看的，Checklist 只做前者。

## 3. 验收步骤

1. 页面顶部圆点变绿、显示"已连接"。
2. 输入框里已经预填了一句目标："下周二安排去上海拜访客户，把事情办妥"，直接
   点"开始任务"。
3. 观察主区域的日志流，应该能看到模型依次去查客户信息、双方日程、差旅政策，
   然后搜索航班（遇到满员）、搜索酒店（遇到超预算），每次遇到问题都有一段
   推理文字说明它怎么应对，最后完成两项预订、同步日历、发确认邮件。
4. 观察右侧 Checklist：随着 `book_flight`、`book_hotel`、`sync_calendar`、
   `send_confirmation_email` 依次成功，对应项应该逐个打勾，"客户会面时间已
   确认"这一项会在航班订好、且此前查过客户日历之后一并打勾。全部完成后应该是
   "5 / 5 项已完成"。

## 4. 关键验收点（延续 Phase 2 的原则，这次改一个新工具试试）

打开 `main.py`，找到 `MOCK_DATA["search_hotel"]`，试着把预算内的那个选项也
改成超预算，比如把"银城中路商务酒店"的价格从 780 改成 850：

```python
{"hotel_name": "银城中路商务酒店", "distance_to_customer_km": 1.8, "price_per_night": 850},
```

**不改任何别的代码**，保存、重新运行，观察模型的反应：三个选项现在全部超预算，
模型应该能看出这一点，并在推理文字里说明它打算怎么办（比如说明现有选项都超
预算、但差旅政策注明当前 demo 未接入审批流程、所以它会选择超预算最少的一个
并在总结里明确标注这是需要人工复核的地方）。这一步跑通了，说明决策确实来自
它现场对新数据的推理，而不是代码里预埋的分支。

## 5. 其它说明

- `_booked_flights`、`_booked_hotels` 是模块级列表，只是为了在单次任务运行内
  模拟"生成递增的订单号/确认号"，每次点"开始任务"都会清空，不是真实状态存储。
- 循环最多跑 14 轮（`MAX_TURNS`，比 Phase 2 的 8 轮宽松一些，因为工具变多了）。
  超过还没结束会强制停止并提示——这本身也是 Phase 6 要记录的一类 Bad Case
  （重复失败/死循环）。
- 还没做的部分：人工审批弹窗（Phase 4）、执行层/决策层二分的最终报告（Phase 5）、
  迭代记录整理（Phase 6，建议全程同步记录而不是最后补）。

## 文件说明

| 文件 | 作用 |
|---|---|
| `main.py` | 后端：10 个假工具 + 工具 schema，`run_agent_loop` 是核心的 Plan→Action→Observation 循环，`_update_checklist` 负责核对客观结果更新 Checklist，`/ws` 负责收发 WebSocket 消息 |
| `static/index.html` | 前端：主区域日志流 + 右侧 Checklist 侧边栏，实时渲染 目标/推理/工具调用/工具返回/Checklist/完成/出错 七种消息 |
| `requirements.txt` | 依赖清单（和之前相同） |
| `.env` | 存放真实 Key（沿用之前已经配置好的，不用重新配） |

## 下一步（Phase 4 预告）

给"超预算需要人工审批"这个场景加一个真正的网页版审批弹窗，而不是像现在这样

Observation 喂回模型继续循环。
