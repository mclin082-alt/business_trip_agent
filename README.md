# Phase 2 运行说明

Phase 1 验证的是"网页 ↔ 后端 ↔ Qwen API 三方连通"，只有一问一答，没有工具、
没有循环。Phase 2 要证明的是整个方案最核心的一件事：

> **下一步该调用哪个工具、失败了怎么办，是模型自己现场推理决定的，不是代码里
> 写死的 if-else 分支。**

## 这一步做了什么

- 定义了 3 个"假工具"（其实是普通 Python 函数，返回写死的假数据）：
  - `get_customer_calendar`：查客户某天的日程
  - `search_flight`：查航班（故意设计成"09:00 满员"这个失败点）
  - `book_flight`：预订航班
- 用模型的 tool use / function calling 能力，让它自己判断"现在该调用哪个
  工具、传什么参数"。
- 写了一个循环（在 `main.py` 的 `run_agent_loop` 函数里）：
  调用模型 → 它说要用哪个工具 → 代码执行那个工具（返回假数据）→ 把结果原样
  丢回去给模型 → 再问模型 → 重复，直到模型这一轮不再调用任何工具（代表它
  自己判断任务完成了）。
- 每一步——目标、模型的推理文字、调用了什么工具、工具返回了什么——都通过
  WebSocket 实时推到网页上，推理文字用高亮样式单独标出来，这是"这是模型在
  决策而不是查表"的直接证据。

## 3. 验收步骤

1. 页面顶部圆点变绿、显示"已连接"。
2. 输入框里已经预填了一句目标："帮我订一张下周二去上海的机票，要赶上客户
   上午10点的会面"，直接点"开始任务"。
3. 观察日志流应该依次出现（具体措辞会因模型而异，但顺序和逻辑应该是这样）：
   - 【目标】你输入的那句话
   - 【推理】模型说明它打算先查一下客户的日程 / 先查航班
   - 【调用工具】`get_customer_calendar` 或 `search_flight`，参数是它自己填的
   - 【工具返回】对应的假数据（比如航班返回"09:00 已满员，可选 07:30/11:30/14:00"）
   - 【推理】模型看到满员结果后，结合"客户 10:00 才有空"这个约束，说明它为什么
     选择改订 07:30（这段文字必须是模型现场生成的自然语言解释，不是提前写好的）
   - 【调用工具】`book_flight`，参数 `07:30`
   - 【工具返回】预订成功、给出订单号
   - 【推理】模型总结任务已完成
   - 【完成】

## 4. 关键验收点（一定要做这一步，这是整个方案的立论根基）

打开 `main.py`，找到最上面的 `MOCK_DATA` 字典，比如把 `search_flight` 的
返回值改一下：

```python
"search_flight": {
    "status": "failed",
    "reason": "09:00 上海航班已满员",
    "available_alternatives": ["11:30", "14:00"],  # 把 07:30 去掉了
},
```

**不改任何别的代码**，保存、重新运行，重新点"开始任务"，观察模型的反应：
它应该会发现 07:30 已经不在可选项里了，重新推理该选哪个（比如发现 11:30 和
14:00 都满足不了"客户 10:00 才有空"这种更早到场的偏好，或者需要重新判断
约束），给出不一样但依然合理的应对——而不是报错卡死，也不是"凑巧"还选中
原来的答案。**这一步跑通了，就证明决策确实来自它现场的推理，不是代码里
预埋的分支。**

你也可以试试把 `status` 直接改成 `"success"`，看模型是不是就不再纠结改
时间这件事、直接进入预订步骤——这也是同一个验证逻辑。

## 5. 其它说明

- `_booked_flights` 是一个模块级列表，只是为了在单次任务运行内模拟"生成
  递增的订单号"，每次点"开始任务"都会清空，不是真实状态存储，后面阶段
  如果要做真正的多轮任务/历史记录，需要单独设计。
- 循环最多跑 8 轮（`MAX_TURNS`），超过还没结束会强制停止并提示——这本身
  也是 Phase 6 要记录的一类 Bad Case（重复失败/死循环），如果你在测试中
  真的撞见了，正好可以直接记一条到迭代记录表里。
- 工具目前都是"假函数"，还没有加人工审批弹窗（那是 Phase 4）、没有 Checklist
  侧边栏（那是 Phase 3）、也没有把 CRM/酒店/日历同步/发邮件这些工具全部
  补齐（也是 Phase 3）。这一步只聚焦"决策链路能不能跑通、能不能验证"这一件事。

## 文件说明

| 文件 | 作用 |
|---|---|
| `main.py` | 后端：定义假工具 + 工具 schema，`run_agent_loop` 是核心的 Plan→Action→Observation 循环，`/ws` 负责收发 WebSocket 消息 |
| `static/index.html` | 前端：目标输入框 + "开始任务"按钮，实时渲染 目标/推理/工具调用/工具返回/完成/出错 六种日志 |
| `requirements.txt` | 依赖清单（和 Phase 1 相同） |
| `.env` | 存放真实 Key（沿用 Phase 1 已经配置好的，不用重新配） |
