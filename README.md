# Phase 4 + 5 运行说明

Phase 3 补齐了全部工具、加了 Checklist 侧边栏。这一步在此基础上做了两件事，
对应方案书的第四节人工审批和第五节最终报告：

1. **人工审批卡片（Phase 4）**：新增一个特殊工具 `request_human_approval`。
   模型判断遇到「预算超出政策上限」或「即将向客户发送确认邮件」这两类场景时，
   必须先调用它，网页上会弹出一张卡片，展示模型给出的理由和打算执行的动作，
   程序会真正暂停，等你点了「批准/拒绝」之后，这个结果才会作为下一个
   Observation 喂回模型继续循环——不是命令行 `input()`，也不会自动跳过。

2. **执行层/决策层最终报告（Phase 5）**：五项 Checklist 全部完成、模型这一轮
   不再调用任何工具时，不直接显示"Done"，而是再单独调用一次模型，让它基于
   本次任务真实发生的工具调用历史和审批记录，生成一份区分两层的总结：
   ✅ 执行层（订单号、确认号这些有客观依据的事实）、⚠️ 决策层（选择的取舍、
   被批准的例外，需要人复核的地方）。

## 这一步做了什么

### 1）审批工具与规则调整

- `MOCK_DATA["get_travel_policy"]` 里"当前 demo 暂未接入审批流程"这句拿掉了，
  现在提示模型遇到超预算要调用 `request_human_approval`。
- 新增工具 `request_human_approval(reason, proposed_action)`，它和其它 10 个
  工具不一样——不是一个查表/返回假数据的普通函数，而是在 `run_agent_loop`
  里被特殊处理：调用后会往前端发一条 `approval_request` 消息，然后
  `await approval_queue.get()` 真正卡住，直到用户点击按钮。
- System Prompt 明确要求两个触发点必须先审批：a) 酒店超预算；b) 正式发送
  确认邮件之前的最终确认。审批被拒绝后，模型需要自己重新想办法，代码不替它
  决定下一步该做什么。

### 2）WebSocket 并发处理

之前 Phase 2/3 里，`websocket_endpoint` 收到 `start_task` 后是直接
`await run_agent_loop(...)`，整个连接会被这一次任务阻塞住，没法在任务跑到一半
时再接收别的消息。审批卡片需要"任务还在跑、同时又能收到用户点击结果"这种并发
能力，所以这次把 `run_agent_loop` 改成用 `asyncio.create_task` 起的后台任务，
外层 `while` 循环继续 `receive_text()`，收到 `approval_response` 就塞进一个
`asyncio.Queue`，`run_agent_loop` 里挂起等待的 `approval_queue.get()` 就会被
唤醒，循环得以继续。

### 3）最终报告怎么生成

任务结束（模型不再调用工具）且 Checklist 5/5 全部完成时，`generate_final_report`
会用一份**重新整理过的、干净的事实清单**（目标、Checklist 状态、完整的工具调用
历史、审批记录）单独调用一次模型，要求它只输出 JSON：
`{"execution_layer": [...], "decision_layer": [...]}`。

**为什么不直接复用主循环那一长串 `messages` 历史？** 因为主循环的上下文里混杂
了大量推理文字、失败重试的过程，直接续着问"总结一下"容易被前面的叙述带偏；
单独整理一份紧扣真实记录的输入，能让报告更贴着"实际发生了什么"来写，而不是
被模型自己前面说过的话影响。

## 3. 验收步骤

1. 页面顶部圆点变绿、显示"已连接"。
2. 输入框里已经预填了目标，直接点"开始任务"。
3. 观察日志流：模型查客户信息、双方日程、差旅政策，然后搜索航班（遇到满员，
   自己改订 07:30）、搜索酒店（遇到超预算的近距离选项，但 mock 数据里还给了
   一个 780 元、在预算内、距离稍远（1.8km）的选项）。

4. **关键验收点 1（酒店这一步允许出现两条合法路径，都算通过）**：

   > ⚠️ 修订说明：v1.1 版本这里曾写死"酒店超预算之后必然弹出审批卡片"，
   > 这个预期是错的。方案书 5.3 节的原意是让模型自己在"选更远但合规的酒店"
   > 和"申请超预算例外"之间做权衡，`main.py` 的 mock 数据里恰好放了一个
   > 780 元的合规选项（银城中路商务酒店），所以模型选择直接预订它、不触发
   > 审批，是完全合理、符合 System Prompt 规则的决策，**不是 bug**。
   > 详见本文档末尾「设计澄清记录」。

   跑一次流程，实际会落在下面两条路径之一，**两条都算验收通过**：

   - **路径 A（更常见）：模型判断"有合规选项就该用"，直接预订银城中路商务
     酒店（780 元），不触发审批。**
     验收方式：日志流里应该能看到模型的推理文字明确对比了三个选项的价格和
     距离，说明了"为什么选这个而不是更近但超预算的两个"，比如提到通勤距离
     的 trade-off。工具调用应该是 `book_hotel(hotel_name="银城中路商务酒店",
     price_per_night=780)`，中间**不会**出现酒店相关的 `request_human_approval`
     调用——这是对的，不用等审批卡片弹出。

   - **路径 B（模型判断"离客户更近"的价值更高时会走这条）：模型选择超预算
     的近距离酒店（950 或 920 元），调用 `request_human_approval`，网页弹出
     黄色卡片，展示理由和打算预订哪个酒店。**
     验收方式：程序应该真的停住——不点按钮，日志流不会继续往下走。点"批准"
     后卡片变灰显示"✓ 已批准"，日志流继续，模型会真的去预订那个超预算酒店。

   如果你想稳定复现路径 B（比如面试演示希望必然看到审批卡片这一步），可以
   把 `main.py` 里 `MOCK_DATA["search_hotel"]["options"]` 里那个 780 元的
   选项价格改到 800 以上，让"附近所有选项都超预算"这个 mock 设定名副其实。
   但**不建议**为了让演示更"听话"而这样改——这等于用 mock 数据反向限制模型
   的判断空间，和方案书里"不能用预设分支冒充现场决策"的原则精神上是相通的。
   保留两条路径反而更能证明"下一步怎么走是模型现场推理的"这个核心命题。

5. 无论走的是路径 A 还是路径 B，继续往后，都应该再看到一次审批卡片——发
   确认邮件之前的最终确认（这一步是硬性规则，不管酒店怎么选都必须走）。
   批准后邮件发送成功，Checklist 五项应该全部打勾。

6. **关键验收点 2（最终报告是不是基于真实记录写的）**：全部完成后，应该看到
   一张"完成"日志之前多了一张报告卡片，✅ 执行层部分应该能对上你刚才实际看到
   的订单号/确认号/event_id/message_id；⚠️ 决策层部分：
   - 如果走的是路径 A，应该提到"选择了更远但合规的酒店"这个 trade-off
     （比如通勤距离、退改灵活度），而不是空话；
   - 如果走的是路径 B，应该提到那次酒店超预算审批的具体金额和理由。

## 4. 关键验收点（延续 Phase 2/3 的原则，测试"拒绝审批"这条路径）

正常跑一次流程，如果这次走的是路径 B（酒店超预算触发了审批卡片），在卡片
弹出时点"**拒绝**"，观察：

- 模型是不是真的重新想了别的办法（比如它会不会说"没有别的合规选项了，需要
  重新考虑"，或者转而选择合规的银城中路商务酒店），而不是无视拒绝结果继续
  订原来那个酒店。
- 如果它确实无法在不超预算的情况下完成任务，观察它最后怎么收尾——这本身就是
  一个值得记录进 Phase 6 迭代表的真实场景（可能是"结论型错误"或者需要你去
  改 Prompt 让它在无解时给出更清晰的说明，而不是卡住）。

如果这次跑的是路径 A（酒店没触发审批），可以直接测试发确认邮件之前的那次
审批——同样点"拒绝"，观察模型是否会重新征求确认或者说明原因，而不是无视
拒绝继续发送。

这一步跑通了，说明"要不要发起审批、被拒绝之后怎么办"确实来自模型现场推理，
而不是代码里预埋的分支——代码只负责暂停/等待/转发这三件事。

## 5. 其它说明

- `MAX_TURNS` 从 Phase 3 的 14 调到 16，因为审批交互会多占用一两轮。
- 如果你在等审批卡片的过程中刷新页面或断开连接，后台任务不会自动清理审批
  记录——这是一个已知的简化，demo 场景下不需要处理更复杂的会话恢复逻辑。
- 还没做的部分：Phase 6 迭代记录整理（这是文档工作，不是代码工作，建议在你
  跑上面这些验收步骤时，把模型判断错的地方随手截图，最后整理进方案书 6.2
  那张表）。

## 设计澄清记录（不是 Bad Case，是验收脚本本身的假设错误）

这条记录不属于方案书 6.1 定义的四类 Bad Case（那四类都是"模型判断错了"），
但同样值得记录，因为它反映的是评估设计本身的一个漏洞，价值不亚于一条真实的
Bad Case——**建议收进 Phase 6 展示环节，作为"我不仅在挑模型的错，也在挑自己
验收脚本设计的错"的例子。**

| 项目 | 内容 |
|---|---|
| 触发场景 | 酒店超预算搜索结果里，`options` 中恰好有一个在预算内的较远选项（银城中路商务酒店，780 元，1.8km） |
| 最初的预期（README v1.1） | 酒店超预算之后必然触发 `request_human_approval` 审批卡片 |
| 实际发生的 | 模型直接选择了合规的 780 元选项预订，未触发审批，理由是"陆家嘴近距离酒店均超预算，为遵守政策选择距离稍远但合规的选项" |
| 这是模型的错吗 | **不是。** System Prompt 规则 4a 写的是"打算预订的酒店价格**超出**预算上限"才必须审批——这个选项没超，模型没有违反任何规则，推理也清楚地对比了三个选项、说明了取舍 |
| 真正的问题 | README 验收脚本把"设计时设想的一条路径"错误地当成了"唯一正确路径"，没有意识到 mock 数据本身允许模型走向另一条同样合法的分支 |
| 修复动作 | 把 README 验收步骤 4 改成"酒店选择存在路径 A（直接订合规选项）和路径 B（超预算走审批）两种合法结果，两者都算通过"，不再要求审批卡片必然出现 |
| 复测结果 | 通过——两条路径下模型的推理文字和后续 Checklist/报告都能自洽 |
| 这条记录的价值 | 面试展示时可以用来说明：判断"这是模型的问题"还是"这是我预期设定的问题"，本身就是评估工作里容易被忽略但很关键的一步；如果照着最初的预期硬改 mock 数据去"逼"模型必然触发审批，反而会削弱"决策来自现场推理"这个核心论点 |
