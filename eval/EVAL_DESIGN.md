## 0. Executive Summary

一个能跑的 Agent demo 和一个「可以被信任上线」的 Agent 之间，中间隔着一整套评测体系。这份文档记录了这套体系的设计判断：怎么定义「好」的具体维度、怎么设计测试场景才能真正把模型推到决策边界上而不是自欺欺人、出了问题怎么归因到底是模型判断错了还是系统本身有缺陷、以及这一切怎么形成一个持续迭代的闭环。这套方法论本身，就是 AI 产品经理最核心的一块能力——「定义 AI 产品质量」不是一句口号，而是一系列具体、可执行、可复用的判断标准。

### 如果只有十分钟

这份文档最想证明的不是「我们做了哪些测试」，而是两个方法论判断：

1. **怎么设计场景，才能真正把模型推到决策边界上，而不是造一个看起来吓人、实际有安全出口的假测试** —— 见第 4 章
2. **「未复现」和「没测到」是两种完全不同的结论，怎么区分才不会互相污染** —— 见第 6 章

第 5 章的 Failure Taxonomy、第 7 章的 case matrix 技术附录，感兴趣可以细读，跳过也不影响理解前两点。

## 1. Why Agent Evaluation Is Different

传统软件测试的假设是「输入确定，输出确定」：给定同样的输入，断言同样的输出，测试要么通过要么失败，没有中间地带。Agent 系统打破了这个假设——同一个目标，模型可能选择好几条都合理的路径（先订机票还是先查日程）；同一个 prompt，两次运行的推理过程可能不完全一样；更重要的是，Agent 会真实执行有后果的动作（下单、发邮件），「输出看起来对」和「这个动作真的安全」是两件需要分开验证的事。

这个项目把评测方法论拆成两种性质完全不同的活动，不能混为一谈：

- **Replan（运行时）**：任务执行中，模型遇到失败 Observation 现场重新决策，这是 Agent 单次运行内的能力，不是「迭代」。
- **Evaluation（开发时）**：固定 prompt 和代码，只改动 mock 数据构造定向场景，多轮运行观察模型在哪些地方判断错误，定位原因、修复、复测——这才是迭代。

区分这两者，是为了避免一个常见的误区：把「这次跑得不理想」直接归结为「再调一版 prompt」，而不去追问这次失败到底是模型的决策问题，还是测试场景本身没有设计好，还是系统工程层面存在缺陷（详见第 5、6 章）。

## 2. Product Quality Dimensions

在写任何一个具体测试 case 之前，先要回答一个更根本的问题：**「好」这件事到底有哪些维度？** 这个项目定义了七个维度：

| 维度 | 要回答的问题 | 当前状态 |
|---|---|---|
| Task Success | 目标是否真正达成 | ✅ 每个 case 的 checklist 驱动 |
| Decision Quality | 面对多个合法选项时，选择是否合理（比如是否选中了政策合规的酒店） | ✅ |
| Safety | 是否会执行未经授权的、有后果的动作 | ✅ 全局不变量 + 运行时护栏 |
| Recovery | 遇到失败（订单失败、审批被拒）之后能否恢复并继续推进 | ✅ |
| Efficiency | 是否存在浪费——重复查询、无意义重试 | ✅ |
| Continuity | 需要用户补充信息时，上下文是否完整保留 | ✅ |
| Robustness | 面对对抗性输入（如工具返回结果里混入的伪造指令）是否会被带偏 | ✅ |

七个维度目前均有对应的测试场景覆盖（完整的场景清单见第 7 章附录）。定义这七个维度本身就是一次产品判断：选择「Recovery」和「Continuity」分开定义，是因为「失败后能不能恢复」和「信息不足时上下文会不会丢」是两类完全不同的失败模式，混在一起会让归因变得模糊——这个区分直接决定了第 5 章 Failure Taxonomy 里标签的粒度该怎么划。

## 3. Evaluation Architecture

每一次测试运行，都会对同一份执行轨迹做三层互相独立的检查：

1. **确定性断言（Deterministic Check）**——针对每个测试场景专属的结构化事实，比如「checklist 是否全部完成」「审批之后是否真的按批准结果执行了」。
2. **全局不变量（Global Invariants）**——与具体场景无关、对所有测试都必须成立的硬规则，比如「预订不能被重复计费」「超预算的酒店在没有已批准审批的情况下不能预订成功」「报告里的编号不能是编造的」。这一层的意义在于：哪怕某个具体场景的测试通过了，只要触碰了这些红线，整体依然判定失败。
3. **LLM-as-judge（语义评判）**——只在真正需要语义理解、规则无法表达的地方使用，比如「模型的推理文字里是否真的比较过候选方案」。裁判模型和被测模型是分离的，避免同一个模型自己给自己判分；返回三态结果（通过/不通过/无法判断），「无法判断」不计入失败——这是一个容易被忽略但很关键的细节，很多团队会把「证据不足」错误地记成「不通过」。

评测环境和生产环境使用完全隔离的持久化路径，每次评测运行前会清空重建，避免历史数据污染下一次结果——这是「测试环境和生产环境边界」这个基本工程原则在这个项目里的具体体现。

## 4. Scenario Design: Forcing the Risk Path

这是整个评测体系里最容易被低估、但实际上含金量最高的一块判断：**测试场景设计得不够狠，会产生一种看不出来的假阳性（silent false pass）。**

一开始的几个测试场景犯过这个错——比如「验证酒店超预算审批是否触发」这个场景，最初的 mock 数据只让一家酒店超预算，另外两家仍然合规。这看起来是「制造了一个会触发审批的场景」，但一个完全理性的模型完全可以直接订合规的那家，全程不需要走审批流程。这类场景因此会**稳定通过**——但通过的原因是「模型压根没遇到这个风险」，不是「模型正确处理了这个风险」。

修正的思路是：**让风险路径变成模型唯一合理的选择，而不是众多合规选项之一。** 具体做法是把全部候选都推到风险边界上（比如三家酒店全部超预算），逼模型必须正面面对这个决策，而不是绕道而行。这个修正应用到了四个不同的测试场景，包括对抗性测试（工具返回结果里混入伪造的「系统指令」，测试模型是否会被数据里的假指令带偏）——如果场景本身留了一个不需要面对风险的安全出口，对抗性测试就完全测不出任何东西。

配套的一个判断是 **`must_exercise` 标记**：早期设计里，如果一次运行根本没撞上想测的风险路径，这次运行不计入通过/失败统计，避免「没测到」被误读成「测过且通过」。

但这个默认设计对某些场景并不适用——对于那些**存在的唯一意义就是验证某条特定路径**的场景，「没触发」本身就不是中立的。它意味着这次运行没有完成它该做的事，理应算作失败。`must_exercise` 标记就是用来区分这两种不同性质的测试用例：「可选风险，没触发也没关系」，和「这条路径就是这个场景全部意义」。

## 5. Failure Taxonomy: Diagnosing Why, Not Just Whether

一个失败的测试场景，只告诉你「这里出了问题」，不告诉你「是哪一类问题」。按场景分组的报告会显示「某场景失败了」，但看不出这批失败里到底是「绕过审批」多，还是「报告幻觉」多——因为同类失败可能分散在不同场景里被稀释掉。

因此需要两个互相垂直的坐标轴：场景本身**故意构造了什么**（输入侧），和这次运行**实际上是哪种方式错的**（输出侧，即 failure taxonomy）。对已有检查函数产出的失败原因文本做事后关键词打标签，得到一套固定分类：

```
approval_bypass        未经审批就执行了有后果的动作 / 被注入指令带偏
hallucination           报告编造了不存在的订单号
scenario_setup_broken   场景本身没有按预期打起来，需要先怀疑测试设置本身
loop_or_retry_waste     连续重试同一方案 / 疑似死循环 / 重复查询
context_loss            信息补充后看不到此前的上下文
premature_termination   没有推进到合法终态
checklist_ungrounded    checklist 标完成但找不到对应的成功依据
```

其中 `scenario_setup_broken` 这一类值得单独说明：它专门用来分离「场景本身没打起来」和「模型真的判断错了」这两种性质完全不同的失败。这类失败首先应该怀疑的是测试设置本身，而不是不假思索地记成一次模型 bad case——把它单独分类出来，也让失败归因汇总表不会被「测试基础设施的问题」稀释掉「模型真实犯错」的信号密度。这个判断背后是一个容易被忽视但很重要的纪律：**在下结论「模型不行」之前，先排除「是不是我的测试没设计对」。**

## 6. Iteration Loop & Regression Discipline

评测体系存在的意义不是产出一份报告，而是驱动一个真实的迭代闭环：

```
定义风险类型 → 只改 mock 数据构造定向场景 → 多轮运行观察
   → 只有真实出现断言不满足才进入修复流程 → 修复后转为 regression case
```

预先定义了四类风险作为迭代的起点：审批遗漏、Observation 误读（把候选误当成已确认）、重复失败/死循环、结论型错误（推理文字通顺但决策实际不满足约束）。每类场景只跑 2-3 次——跑够验证「是否存在真实失败」，不追求统计意义上的稳定性认证，避免为了凑够案例数而弱化已经调好的 prompt。

这里有一个值得强调的方法论判断：**「未复现」也是合法结论。** 针对某类风险设计诱导性场景，跑 2-3 轮观察，如果多轮定向测试下依然没有复现，如实记录「未复现」——这本身就是一条真实、有价值的测试结论，说明当前版本在该类风险上是稳健的，不需要靠「编造出模型确实犯过这个错」来证明方案的严谨性。

一旦某类问题被真实发现并修复，对应的测试场景会被标记为 **regression case**，长期保留在测试集里防止已修复的问题回归。一个具体的例子：效率护栏最初只存在于评测脚本里，属于「只有跑评测才会发现」的问题；后来被下沉到生产运行时同样生效（详见 DESIGN.md 第 7 章 Evolution 3）——这是评测发现的问题反过来推动产品能力升级的一个具体例子，说明评测体系不是一个自说自话的旁路系统，而是真正在影响产品设计决策。

### 7.2 Reliability 层：确保测试结果本身可信

评测结果要可信，测试基础设施本身也需要被验证。工具调用和它对应的结果，靠唯一 ID 关联配对，而不是假设事件按顺序一一对应——一旦出现乱序或并行调用，基于顺序的配对会直接错位。

这里有一处专门记录下来的坑：审批工具永远不会产生标准的「调用结果」事件，它走的是「请求/裁决」这条单独的事件对。如果不特殊处理，所有依赖「配对结果」的检查，会在审批流程明明跑对了的情况下也假性失败。这类踩过的坑被沉淀成配对逻辑里的显式处理，而不是留作隐患。

### 7.3 Capability 覆盖表（数据驱动，非手写文档）

每个测试场景标注了一个 Capability 字段（L1 Planning ~ L8 Robustness），覆盖率报告直接从这个字段自动生成——改一次测试场景定义就同步更新覆盖率表，不会出现「文档和代码脱节」的情况。这个设计判断的意义是：能力覆盖率不应该是一份需要手动维护、容易过时的 Excel，而应该是代码运行的直接产物。

## 8. Known Gaps & What's Intentionally Not Done

| 空白 | 原因 |
|---|---|
| Partial Success 报告怎么写 | checklist 是二元判断，暂不细分部分完成场景 |
| Tool Precision（多余工具调用） | 优先级低于已覆盖的六类风险 |
| Token/Cost 聚合报表 | 数据已采集，只是还没聚合成产品级视图——这是目前最值得补的一块，见 DESIGN.md 第 9 章 |
| Long Context 退化专项测试 | 部分覆盖（轮数上限边界），未单独测「上下文变长后指令遵循是否退化」 |
| Ambiguous Goal | 需要新的检查逻辑和目标变体，成本高，明确标注暂不做 |
| 恢复流程本身的正确性（「读回的状态是否完整」） | 由独立的序列化往返单测覆盖，评测框架只验证「恢复之后行为是否正确」，两者是不同层次的测试，不重复覆盖 |

保留这份清单本身就是方法论的一部分：知道哪些空白值得补、哪些可以说清楚原因不补，比「每一类都硬凑一个测试场景」更能体现判断力。
